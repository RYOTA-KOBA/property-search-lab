# 本番想定のシステム構成

## 解こうとしている課題

Rails + Aurora MySQL で物件データを管理し、JSON API として提供している。
物件検索は「価格帯・間取り・駅徒歩分数・エリア・設備」など複数条件の絞り込みに
全文検索とソートが重なるため、RDB の複雑な WHERE 句と JOIN がボトルネックになりやすい。

これを CQRS 的に分離し、**更新系は RDB を正とし、検索系は OpenSearch に寄せる**構成が
有効かどうかを判断したい。

## 全体構成

```
[更新系]
  Rails ──> Aurora MySQL(正のデータストア)
                │ binlog
                v
              DMS(CDC)
                │
                v
          Kinesis Data Streams
                │
                v
          Lambda(非正規化・整形)
                │
                v
            OpenSearch

[検索系]
  Client ──> ALB ──> Rails 検索API ──> OpenSearch ──> JSON 整形して返却
  Client ──> ALB ──> Rails 詳細API ──> Aurora MySQL ──> JSON 整形して返却
```

## API の責務分割

| エンドポイント | データソース | 理由 |
|---|---|---|
| 一覧・検索 | OpenSearch | 非正規化済みドキュメントをそのまま返せる。RDB への JOIN / N+1 が発生しない |
| 詳細1件取得 | Aurora MySQL | 最新性と正確性が要る。CDC のラグの影響を受けさせない |
| 更新系 | Aurora MySQL | 正のデータストア |

検索用ドキュメントは「一覧表示に必要な項目だけを持つ非正規化 JSON」として設計する。
これにより OpenSearch のレスポンスをほぼそのまま API レスポンスに変換でき、
DB がボトルネックになる問題を根本から回避できる。

## なぜ Lambda を挟むのか

DMS の OpenSearch ターゲットは **1テーブル = 1インデックス、1行 = 1ドキュメント**の
単純なマッピングが基本で、複数テーブルを JOIN して1ドキュメントにする変換ができない。

物件検索のドキュメントは `properties` + `property_images` + `property_stations` を
結合した形にしたい。そのため DMS のターゲットを Kinesis にし、
Lambda で関連テーブルを引き直して非正規化する構成を採る。

この非正規化ロジック(`build_document` 相当)が、この検証で最も価値のある成果物になる。

## インデックス設計の方針

- **エイリアス経由でアクセスする。** 実体は `properties_v1`, `properties_v2` … とし、
  アプリは常に `properties_search` エイリアスだけを見る。
  マッピング変更時は新インデックスを作って流し直し、エイリアスを張り替えることで無停止入れ替えができる
- **`_id` は MySQL の主キーと一致させる。** CDC の UPDATE が「新規追加」ではなく
  「同じドキュメントの上書き」として扱われるようにするため
- **`dynamic: strict` にする。** 想定外のフィールドが混入したら気付けるようにする
- 日本語の物件名・住所検索のため kuromoji analyzer を使う
- 「駅から徒歩◯分」だけでなく緯度経度による円形検索を想定し、`location` は `geo_point` 型にする
- 絞り込み条件は `bool.filter` に入れる。スコア計算をせずキャッシュも効く。
  関連度を評価したいキーワード検索だけ `must` / `should` に入れる

マッピングの実体は @reference/index-mapping.json を参照。

## 整合性の担保

CDC は DMS タスクの一時停止・エラー・binlog 保持期間超過などで取りこぼしが起きうる。
そのため以下の二段構えにする。

1. **CDC** — リアルタイム反映用
2. **定期フルリインデックス** — 整合性の保険。Sidekiq の夜間バッチで全件を RDB から
   読み直して OpenSearch に再投入する

## この構成の弱点(検証で確かめるべきこと)

- **結果整合性**: 登録した物件が数秒〜数分検索に出てこない。不動産のように
  早い者勝ちの側面がある業務で許容されるかは、実測値をもとに業務側と合意が必要
- **運用コスト**: OpenSearch クラスタのバージョンアップ、シャード設計、ノードサイジングは軽くない
- **そもそも必要か**: 適切な複合インデックスやリードレプリカで RDB のまま捌ける可能性がある。
  物件数が数万〜数十万件程度なら過剰設計になりうる。
  **導入前にスロークエリログと DB の CPU/IO 使用率でボトルネックを実測すること**
